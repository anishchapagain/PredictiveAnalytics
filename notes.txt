=================================================================
VISION
=================================================================
Agentic AI reporting platform. User submits a request/input, the
agent interprets it and acts accordingly (e.g. query data, run
analysis, generate a report/visualization) rather than the system
exposing only fixed, pre-built reports.

=================================================================
PHASING (decided 2026-08-18)
=================================================================
Build in two phases rather than all at once:

  Phase 1 — API-driven platform, NO LLM/agent yet.
    DB, async API, config, logging, default dashboard. Fully
    deterministic and testable on its own.

  Phase 2 — Layer the agentic/LLM piece onto the Phase 1 platform.
    The agent becomes a client of the Phase 1 API; MCP sits between
    agent and data at this point.

Rationale: DB/API decisions are stable engineering choices; agent/
LLM-framework choices are the most volatile part of the design and
easiest to validate once they sit on an already-correct foundation.
The Phase 1 API is not throwaway work — it's what the agent and MCP
layer call in Phase 2.

Design constraint carried back into Phase 1 so it isn't a rewrite
later:
  - Shape endpoints as granular/composable "tool-like" calls
    (agent-consumable), not just a few broad aggregate endpoints
    convenient only for the dashboard.
  - Logging should carry a caller/actor field from the start (human
    via dashboard vs. later, agent via MCP) so Phase 2's agent-action
    tracing doesn't require replumbing logging.
  - Sketch the permission/access-control model now even if minimal —
    "MCP for data safety" is fundamentally an access-control problem,
    better bolted on top of an existing model than retrofitted.

  caller/actor field called for in PHASING below was NOT added (see

=================================================================
FUNCTIONAL REQUIREMENTS
=================================================================
1. Agentic core [Phase 2]
   - Accepts user input (natural-language request presumably).
   - Interprets intent and "deals accordingly" — i.e. decides what
     data/action is needed and executes it.

2. Persistence [Phase 1]
   - Data moves into a database (currently it's a single raw CSV,
     Business_Report.csv — 233 MB, 1.43M rows of remittance
     transactions). DB replaces/augments the flat file.

3. MCP for data safety [Phase 2]
   - Use Model Context Protocol as the layer between the agent and
     the data, so the agent doesn't get raw/unrestricted DB access.
   - Intent (as stated): safety/guardrails around what the agent can
     read or do with the data.

4. Default dashboard [Phase 1] -- DONE (basic version, 2026-08-19)
   - A baseline dashboard ships out of the box (not agent-generated)
     for standard reporting/visualization. Built as a plain HTML/JS
     page (app/static/dashboard/), chosen over Streamlit when asked
     directly -- see PROGRESS below. A richer dashboard (Streamlit or
     otherwise) is still a separate, open decision if ever wanted.

User asked "how is Baseline funding level determined?" -- answer:
it wasn't calculated at all, a plain user-typed number (unlike

recommended option:

- New endpoint POST /api/v1/forecast/baseline-suggestion (reuses

  accurate than approximating from Prophet's fitted history, and
  works before a forecast has even been run).

  weighted_average (EWMA, recency-weighted), median (resistant to

  with a visible note when less history exists than requested.
- Refactored to avoid duplication: extracted DimensionFilters as a
  shared Pydantic base (ForecastRequest and the new
  BaselineSuggestionRequest both inherit it, same validator) and
  _resolve_dimension_filters()/_run_or_raise() as shared helpers in
  routes_forecast.py, mirrored by buildDimensionFilters()/
  dimensionFiltersError() in the dashboard's own JS.

Verified the same way as every other pass: real HTTP calls against

1. Day-by-day forecast data table now has a Weekday column (Sat,

PROGRESS (2026-08-20): Full /api review -- 3 new endpoints, full
OpenAPI 3 completeness pass across every existing schema
=================================================================
Asked to review the whole API against the dashboard and everything
built so far, add endpoints if genuinely needed, and bring the
OpenAPI 3 document up to a complete/standard shape.

Reviewed first, built second: enumerated every fetch() call the
dashboard actually makes (all 5 meta endpoints + both forecast
endpoints -- nothing orphaned, nothing missing that the dashboard
itself needs) before deciding what, if anything, to add. Concluded
the dashboard alone didn't justify a new endpoint, but two other
gaps did:

New endpoints:
- GET /api/v1/meta/summary -- dataset-wide overview (total_rows,
  TRN_Date min/max, distinct counts per key column). This is CLAUDE.md's
  own schema table, live -- verified it against those exact
  documented numbers (1,430,655 rows; 24/71/102/178/11/13/35 distinct
  counts; 2024-01-01..2026-07-31) and every one matched exactly.
  Previously this was only knowable by reading static docs or
  re-running the EDA report.
- GET / -- orientation endpoint (links to /docs, /redoc, /dashboard/,
  /health, /ready). The service had no landing page at all before.
- GET /ready -- readiness (actually attempts repository.load(),
  503 on DataSourceError), distinct from the pre-existing GET
  /health which is deliberately liveness-only (never touches the
  data source, so it stays meaningful even when that's down). New
  "system" OpenAPI tag groups all three, separate from forecast/meta.

OpenAPI 3 completeness pass across every existing schema/route:
- Every request AND response field across every model now has a
  `description` -- ForecastRequest.horizon_days/growth/interval_width/
  etc., every ForecastMeta/ForecastPoint field, BaselineSuggestionResponse
  fields, SeasonalityIn/HolidayIn fields -- previously several had none.
- ForecastResponse.summary was a bare `dict` -- correct on the wire
  but opaque in the schema itself ({"type":"object"}, no properties).
  Replaced with a fully-typed ForecastSummary model (all 6 fields
  named/typed/described) -- zero change to the actual JSON shape,
  confirmed by re-running a live forecast before/after and diffing.

PROGRESS (2026-08-27, later still): forecast accuracy evaluation
(backtest) -- engine method, endpoint, dashboard card, docs
=================================================================
Raised as a question first ("Did we also calculate the
Evaluations?"), answered honestly (no, nothing existed), proposed a
concrete plan, then built on "lets start building it."

Method chosen: a single train/test holdout, not Prophet's own
rolling-origin cross_validation()/performance_metrics()
(prophet.diagnostics) -- that refits repeatedly and can take
minutes on one corridor, which fits an offline batch job, not an
interactive dashboard button. A single holdout costs roughly one
extra forecast run (confirmed live: ~2s warm cache, ~15s only on a
cold CSV load same as any other endpoint). Documented as a real
caveat, not hidden: one held-out window is itself only a sample,
same underlying issue as the existing sparse/spiky-corridor
caveat, just on the test side instead of the funding side.

TreasuryEngine.evaluate_accuracy() (app/forecasting/engine.py):
hides the most recent eval_days of real history, fits on
everything before that, forecasts exactly the hidden window,
compares against what actually happened. train_forecast() gained
an optional horizon_days override (backward compatible, defaults
to the config's own value when omitted) so the backtest fit can
project forward exactly as many days as it held out, independent
of whatever horizon_days the caller's main config specifies.

Metrics, each a deliberate choice:
- MAPE, computed over non-zero-actual test days only. Real thin
  corridors have true zero-volume days (prepare_data's own
  reindex-with-zero-fill), and percentage error is undefined at
  actual=0 -- considered SMAPE (handles zero gracefully) but chose
  MAPE-with-exclusion-and-disclosure instead, since the dashboard's
  audience is treasury managers, not statisticians, and "excluded
  N zero-volume days, here's the count" is far more explainable
  than introducing SMAPE as a new concept.
- RMSE, computed over every day, no zero-actual blind spot -- the
  "always trustworthy" companion metric.
- interval_coverage_pct: actual vs. [yhat_lower, yhat_upper],
  checked against the configured interval_width -- tests whether
  Prophet's own stated uncertainty is honest.
- safety_stock_coverage_pct: actual vs. the real funding
  recommendation (yhat_upper + safety_buffer_pct) -- more directly
  actionable than interval coverage alone, since it answers "would
  the funding plan actually have been enough," this app's real
  purpose. Deliberately reported alongside interval_coverage_pct
  rather than instead of it.
- A naive-baseline comparison: a flat prediction (trailing mean,
  same as suggest_baseline(method="average")) over the same window,
  with its own MAPE/RMSE, so a caller can see whether Prophet is
  actually earning its keep over "just fund the recent average
  every day." Chose this over a generic persistence-forecast
  baseline specifically because it ties back to a decision this
  project's own users might actually be weighing.

Schema design: EvaluationRequest(DimensionFilters) duplicates
ForecastRequest's model-shaping fields (seasonality, holidays,
changepoint_prior_scale, interval_width, growth,
baseline_funding_level, safety_buffer_pct) rather than subclassing
ForecastRequest -- considered inheriting directly, but
horizon_days there means "days to forecast into the future," which
isn't what this endpoint does, and an inherited-but-misleading
field in the OpenAPI schema would have been a real regression
against this session's own documentation-completeness discipline.
Considered a shared mixin base class to avoid the duplication
entirely; deferred as a bigger, riskier refactor of already-shipped
schemas than "lets start building it" called for -- noted as a
nice-to-have, not blocking.

New endpoint: POST /api/v1/forecast/evaluate, same
_run_or_raise/ValueError->422/DataSourceError->503/
ForecastingError->500 pattern as every other route.
operation_id=evaluateForecastAccuracy. Verified against the live
/openapi.json: zero missing descriptions on the new schemas,
request+response examples both present, matching the completeness
bar set by the 2026-08-20 API review.

of a test suite):
1. App bug -- within_interval/within_safety_stock and the two
   coverage percentages were computed from unrounded floats while
