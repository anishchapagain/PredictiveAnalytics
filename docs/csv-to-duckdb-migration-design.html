The problem, precisely

Business_Report.csv is 233MB, 1.43M rows. CSVDataRepository loads the whole thing into a pandas DataFrame and caches it by file mtime — which works, but has a ceiling that's already visible today, not hypothetical:

  • A cold load takes 30–45 seconds — measured directly against the real file this session, not estimated.
  • Several endpoints hit at once on a cold cache each independently re-parse the entire file in parallel — a real, already-logged bug (TODO.md, Tier 3).
  • Every query — even SELECT one country's distinct agents — first pays the cost of materializing all 1.43M rows in Python, then filters.

None of this is a defect in how app/data/repository.py was written — it's the ceiling of the format itself. A flat file has no index, and pandas has no way to read only the rows a query needs.

Adding data — the question that matters

This is what actually decides the design, more than raw speed: how does adding historic data (an older backfill) or the newest export differ? Under the proposed design, it doesn't — same mechanism either way.

Duplicate protection, decided If two Parquet exports happen to overlap in date range, rows could double-count. Control_No (the schema's own unique transaction id) is deduplicated at query time by default, so an accidental overlap is harmless instead of quietly inflating volume.

Migration plan

Phase 1

Swap the repository, prove nothing else moved

Convert Business_Report.csv → data/business_report.parquet once. Build DuckDBDataRepository behind the exact same load() -> pd.DataFrame contract CSVDataRepository already satisfies — reads data/*.parquet, dedups by Control_No, invalidates its cache off the folder's file listing (not one file's mtime). Add a test using the same fixture pattern already in tests/conftest.py. Flip Settings.data_backend to "duckdb". The full existing test suite (38 tests) should pass unmodified — that's the actual proof this stayed below the line.

Phase 2

Push the real query work into SQL

Optional, separate follow-up, not required for Phase 1 to work: the meta endpoints' nunique()/groupby() calls currently run in pandas after load() returns the full table. Rewriting them as SQL run directly against the Parquet files is where the deepest performance win actually lives — Phase 1 alone already fixes the cold-load ceiling, this is the next increment on top of it.

Risks & decisions already made

  • Duplicate rows across files — decided: dedup by Control_No at query time (see the callout above).
  • Cache invalidation across many files — a directory listing (filenames + mtimes) replaces the single-file mtime check; still no restart needed to pick up new data, same as today.
  • New dependency risk — duckdb installs cleanly with a prebuilt wheel on this project's actual Python version (confirmed, not assumed); zero external server, so it carries none of a real Postgres instance's operational weight.
  • Reversibility — because DataRepository is a real interface, this is not a one-way door. A future PostgresDataRepository (still on TODO.md) would be the same shape of swap, and CSVDataRepository doesn't have to be deleted — it can stay as the fallback Settings.data_backend already supports.
