From raw rows to a daily series

Prophet expects exactly one input shape: two columns, ds (date) and y (value), one row per day, no gaps. Real transaction data is nothing like that — thousands of rows a day, spread across every corridor and agent, with days that have zero activity at all. prepare_data() closes that gap:

The result is anchored to that filter's own history, not the calendar — a corridor whose data goes quiet in June still forecasts forward from its own last day, not from today.

Inside Prophet: fitting and forecasting

Fitting means Prophet decomposes the historical (ds, y) series into additive components it can each estimate separately, then adds them back together:

Forecasting means running that same fitted model forward past the end of the historical data, for horizon_days more days — the trend extrapolates (linearly, or stays flat, depending on growth), and the weekly/yearly/holiday patterns simply repeat on schedule.

Evaluating forecast accuracy

Everything above answers "what does the model predict." A separate, caller-triggered method, evaluate_accuracy(), answers a different question: how much should that prediction actually be trusted? It backtests the exact same config via a single train/test holdout — hide the most recent eval_days of real history, refit on everything before that, forecast the hidden window, and compare against what actually happened:

Five numbers come out the other side, each answering a different question:

MetricAnswers
mape_pctOn average, how far off was the forecast, as a percentage? Computed over non-zero-actual days only — undefined at actual=0, which real thin corridors genuinely have (see "From raw rows to a daily series" above); excluded days are counted, not silently dropped.
rmseSame question in USD, penalizing large misses more — computed over every day, no zero-actual blind spot.
interval_coverage_pctDid actual volume land inside [yhat_lower, yhat_upper] as often as interval_width claims it should? Tests whether Prophet's own stated uncertainty is honest.
safety_stock_coverage_pctWould the actual funding recommendation — safety_stock, buffer included — have been enough? The more directly actionable number of the two coverage figures.
naive_baseline.*Is Prophet even earning its keep? A flat prediction (the trailing mean — same method as suggest_baseline (method="average")) gets the same MAPE/RMSE treatment, for comparison.

A real worked example — receiver_country=NEPAL, eval_days=14, verified live against the actual dataset:

MAPE279.0%274.9%
RMSE132,361120,139

Safety-stock coverage100.0%—

Trained on 929 days, tested on the last 14 (2026-07-18 to 2026-07-31). Both coverage figures and the naive comparison are real findings, not a demonstration of failure — safety_stock_coverage_pct being far higher than interval_coverage_pct is exactly what a non-zero safety_buffer_pct should do, and Prophet losing to the naive baseline on this particular window is precisely the kind of signal this feature exists to surface, not a bug to fix.

One held-out window is a sample, not a guarantee — most of all on a thin/spiky corridor with little history, the same underlying issue as the sparse/spiky safety-stock caveat elsewhere in this doc, just measured on the test side instead of the funding side. Prophet's own rolling-origin cross_validation() (prophet.diagnostics) would average over many windows for a steadier answer, at the cost of refitting repeatedly — minutes, not seconds, on one corridor. That cost is why evaluate_accuracy() deliberately uses one holdout instead: cheap enough to be an interactive dashboard button, not a batch job.
